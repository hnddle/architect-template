# 코딩 원칙

이 문서는 구현 에이전트가 지킬 설계·코딩 원칙을 정의합니다. 언어 · 프레임워크에 종속되지 않는 원칙만 다룹니다. 스택을 고른 뒤 생기는 세부 규칙(프레임워크 관례 · 빌드 · 배포)은 프로젝트가 `.claude/rules/` 에 조건부 규칙으로 더합니다(`CLAUDE.md` 「규칙」).

## 1. 역할 경계

아키텍처 결정과 구현은 담당이 다릅니다. 이 경계를 넘는 순간이 가장 큰 사고 지점입니다.

| 담당 | 산출물 |
| --- | --- |
| 사람 (작성·승인) | FR·NFR, 아키텍처 문서(C4 · ADR), 스택 선택, 인프라·배포 설계, 트레이드오프 결정(ATAM) |
| 구현 에이전트 | 승인된 스펙의 구현과 그 코드 수준 설계(클린 아키텍처, 패턴 적용)만 |

1. 계층·컨테이너·컴포넌트의 정의와 이름은 **반드시** 사람이 승인한 아키텍처 문서를 따릅니다. 에이전트가 계층을 새로 정의하거나 이름을 발명하지 않습니다.
2. 구현 중 승인된 문서와 다른 구조가 필요해지면, 임의로 고치지 않고 **보고**합니다. 어느 쪽이 맞는지는 사람이 판단합니다.
3. 현재 기능의 승인된 스펙(`specs/<NNN>-<name>/`)은 임의로 수정하지 않습니다. 코드와 모순을 발견해도 고치지 않고 보고합니다.
4. 에이전트가 문서 초안을 쓰는 것은 괜찮습니다. 초안은 「승인 대기」로 표시하고, 승인 전 문서를 다음 단계의 근거로 쓰지 않습니다.

요약 : 설계 문서는 사람의 것, 그 문서를 위반하지 않는 코드는 에이전트의 것입니다.

## 2. SOLID 원칙 (반드시)

변경 비용을 낮추는 설계 5원칙이며, 가장 우선하는 코드 수준 원칙입니다. 객체지향이 아닌 언어에서는 「클래스」를 모듈 · 함수 묶음으로 읽습니다.

| 원칙 | 정의 | 구현 시 지켜야 할 것 |
| --- | --- | --- |
| SRP (단일 책임) | 모듈은 변경 이유가 하나 | 두 가지 이유로 수정되는 모듈은 분리 |
| OCP (개방-폐쇄) | 확장에 열리고 수정에 닫힘 | 분기 추가가 반복되는 지점은 인터페이스·다형성으로 교체 |
| LSP (리스코프 치환) | 하위 타입은 상위 타입을 대체 가능 | 구현체가 계약을 좁히거나 새 실패를 더하지 않음 |
| ISP (인터페이스 분리) | 사용하지 않는 메서드에 의존 금지 | 비대한 인터페이스는 역할별로 분리 |
| DIP (의존 역전) | 상위 정책은 추상에 의존 | 도메인 로직에서 구현체 직접 생성 금지, 경계에서 주입 |

실패 케이스 : 한 모듈이 검증·저장·알림을 모두 하면 변경 이유가 셋이 되어, 수정마다 무관한 기능이 회귀합니다.

## 3. 클린 아키텍처 (Clean Architecture)

- **의존 규칙 (절대)** : 의존은 항상 바깥(세부사항) → 안(정책) 한 방향입니다. 도메인 로직은 프레임워크·DB·UI·외부 API를 알지 못해야 합니다.
- 프레임워크와 DB는 세부사항이라 경계 뒤에 둡니다.
- 외부 서비스(결제·문자·메일·소셜 로그인·AI)는 **포트 뒤 어댑터 하나**로 둡니다. 벤더 SDK는 그 어댑터 밖에 나오지 않고, 교체는 설정과 어댑터 하나로 끝나며, 대체된 벤더 코드·설정은 지웁니다.
- 경계를 넘는 데이터는 그 계층의 모델로 변환합니다. 외부 입력은 경계에서 파싱·검증하고, 내부에서는 신뢰합니다 (검증 로직 산재 금지).
- 도메인 간 직접 접근 금지. 다른 도메인은 공개 인터페이스로만 접근합니다.
- 순환 의존 금지.
- **아키텍처 검사가 게이트입니다.** 의존 방향·벤더 격리·순환 금지는 그 스택의 의존 검사 도구나 직접 쓴 시험으로 강제하고, 깨지면 병합하지 않습니다. 경계를 바꿔야 하면 검사를 고치지 말고 보고합니다. 검사 규칙과 컴포넌트 목록의 대응은 `architecture-diagram/component-package-mapping`.

실패 케이스 : UI가 저장 계층을 직접 호출 → 도메인 로직 우회, 테스트 불가. / 두 도메인이 서로의 내부 모듈을 참조 → 순환 의존, 분리 불가.

## 4. 클린 코드 (Clean Code)

- 함수는 한 가지 일만 합니다. 이름은 의도를 드러내고, 이름으로 설명이 끝나지 않으면 분리를 검토합니다.
- 깊은 중첩은 early return·함수 추출로 평탄화합니다.
- 주석은 코드가 표현할 수 없는 제약·이유("왜")에만 씁니다. 나쁜 이름을 주석으로 보완하지 않고 이름을 고칩니다. 의도적으로 단순화한 곳은 `ponytail:` 주석으로 상한과 확장 경로를 적습니다(`conventions.md` §5).
- 오류를 조용히 삼키지 않습니다. 처리하거나, 문맥을 더해 위로 전파합니다.
- 기존 유틸이 있으면 재사용하고, 같은 역할의 새 헬퍼를 만들지 않습니다. 같은 검증 규칙이 두 곳(서버와 화면 등)에 필요하면 각각 한 파일에 두고 양쪽에 같은 사례로 시험을 둡니다.
- 패턴·추상화는 문제가 있을 때만 도입합니다 — **구현체가 하나뿐인 인터페이스, 제품이 하나뿐인 팩토리, 바뀌지 않는 값의 설정**을 만들지 않습니다. 외부 연동 포트는 예외입니다(실제 어댑터와 시험용 가짜, 구현이 둘).
- 표준 라이브러리 · 플랫폼 기능 · 이미 있는 의존성으로 되는 일에 새 의존성을 더하지 않습니다.

## 5. 12-Factor (매우 중요)

어디에 배포하든 같은 코드가 돌게 하는 원칙이라 첫 커밋부터 지킵니다. 서버 프로세스가 없는 산출물(라이브러리 · CLI · 정적 사이트)은 해당하는 행만 적용하고, 적용하지 않는 행을 `CLAUDE.md` 결정 색인에 적습니다.

| # | 요소 | 구현 시 지켜야 할 것 |
| --- | --- | --- |
| I | 코드베이스 | 저장소 하나, 배포 여럿. 환경별 코드 분기 금지 |
| II | 의존성 | 매니페스트에 명시적 선언 · 버전 고정. 전역 설치에 암묵 의존 금지 |
| III | 설정 | 환경에 따라 달라지는 값은 **전부 환경변수**. 코드·설정 파일에 환경별 값 하드코딩 금지 (`security.md` §1) |
| IV | 백엔드 서비스 | DB·큐·캐시는 주소 · 자격 증명만 바꿔 교체하는 연결 자원 |
| V | 빌드·릴리스·실행 | 빌드 산출물은 불변. 실행 단계에서 코드 수정 금지 |
| VI | 프로세스 | **무상태(Stateless)**. 세션·상태는 메모리 · 로컬 디스크가 아니라 백엔드 서비스에 |
| VII | 포트 바인딩 | 포트 바인딩으로 노출. 특정 서버 내장 가정 금지 |
| VIII | 동시성 | 프로세스 수를 늘리면 처리량이 느는 구조 |
| IX | 폐기 가능성 | 빠른 시작·정상 종료. **재시도되는 모든 흐름은 멱등** — 아래 참조. 정기 작업은 실패하면 0이 아닌 코드로 끝냅니다 |
| X | 개발·운영 일치 | 환경 차이 최소화. "로컬에서만 되는" 코드 금지. 개발 설정도 운영과 같은 기본값 |
| XI | 로그 | 표준 출력 이벤트 스트림. 파일 경로 · 전송처를 코드가 정하지 않음 |
| XII | 관리 프로세스 | 이행·정기 작업은 일회성 프로세스로 분리 |

**설정(III)의 두 가지 보충**

- **연동 키가 빠지면 기능을 끄고, 그 상태를 사용자에게 보입니다.** 키가 모두 있을 때만 켜지고, 없으면 호출은 전용 오류 코드로 거절하고 화면은 「연결 전」을 보입니다. 보낸 척 성공을 기록하지 않습니다 — 꾸민 성공은 운영 장애를 숨깁니다. 키가 일부만 있으면 운영 설정은 빠진 이름을 대며 기동에 실패합니다.
- **서비스 기준 시간대는 환경변수가 아니라 코드 상수입니다.** 환경마다 같은 기록이 다른 날짜로 묶이면 안 되기 때문입니다. 상수는 실행 단위(서버 · 클라이언트)마다 한 곳에만 두고, 여러 곳이면 값이 같은지 시험이 확인합니다.

**멱등성(Idempotency) 규칙** : 프로세스는 언제든 중단·재시작될 수 있으므로(IX), 재시도가 존재하는 모든 흐름은 같은 입력을 2회 실행해도 결과가 같아야 합니다. 중복 전송 시 무슨 일이 일어나는지를 설계에 명시하고, 멱등 키·중복 검사 등 수단을 함께 구현합니다. 멱등 키는 확정 순간에 요청하는 쪽이 만들고 재전송도 같은 값을 보냅니다.

요약 : 설정은 환경변수로, 프로세스는 무상태로, 재시도는 멱등으로, 로그는 스트림으로 — 이 네 가지가 구현 단계의 핵심입니다.

## 6. 품질 기준 (ISO/IEC 25010 · ATAM · Four Golden Signals)

- **ISO/IEC 25010** : NFR은 이 표준의 품질 특성을 어휘로 씁니다. 2023년판 기준 아홉 가지 — 기능 적합성 · 성능 효율성 · 호환성 · 상호작용 능력(사용성) · 신뢰성 · 보안성 · 유지보수성 · 유연성(이식성) · 안전성.
- **ATAM** : 품질 특성 간 트레이드오프(예: 성능 vs 보안)는 사람이 결정합니다. 구현 중 발견하면 임의 선택하지 않고 보고합니다.
- **Four Golden Signals** : 지연시간 · 트래픽 · 오류 · 포화도를 관측할 수 있게 구현합니다. 구조화 로깅을 기본으로, 외부 호출 · 주요 처리 경로에는 소요 시간과 실패를 기록합니다.

## 7. 보안 설계 (OWASP)

보안 결함은 설계 단계에서 차단합니다. 기준은 OWASP Top 10, 구체 규칙은 `security.md`가 정본입니다. 인증 · 인가는 모든 진입점에서 처리 전에 하고("내부에서만 호출된다"는 가정 금지), 판단이 불가능하면 거부합니다(Fail Secure).

## 8. 문서 체계 (C4 모델 · ADR)

아키텍처 문서는 C4 모델(Context → Container → Component)과 ADR로 사람이 작성·승인합니다(`docs/04.design/`). 에이전트는 구현 전 상위 문서(스펙 → 아키텍처 → SRS)를 읽고, 정의된 경계와 이름을 그대로 쓰며, 하위 산출물이 상위 문서와 모순되면 작성을 중단하고 보고합니다.

요약 : 경계는 사람이 정하고 검사가 지키며, 에이전트는 그 안에서 단순하게 구현합니다.
