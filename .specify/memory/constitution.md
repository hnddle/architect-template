# <서비스 이름> Constitution

이 문서는 이 저장소에서 코드 · 스펙 · 계획을 만드는 모든 작업에 걸리는 **상위 게이트**다.
세부 규칙의 정본은 `.claude/rules/` 이며, 이 문서는 그중 **위반 시 작업을 중단시키는 것**만 원칙으로 올린다.
충돌하면 이 문서가 이긴다. 헌법의 현재 상태는 맨 아래 **Version 줄이 정본**이다 — 다른 문서가 헌법 상태를 문장으로 옮겨 적지 않는다.

## Core Principles

### I. 승인된 문서가 정본이다 (역할 경계)

요구사항(`docs/03.srs/`)과 아키텍처 문서(`docs/04.design/`)는 사람이 소유한다.

- 계층 · 컨테이너(`CON-*`) · 컴포넌트(`CMP-*`)의 **이름과 경계를 발명하지 않는다**. 목록의 정본은 <C4 컨테이너 · 컴포넌트 문서 경로> 이며, 코드의 모듈 이름은 그 ID가 정의한 이름에서 가져온다.
- 구현 중 문서와 다른 구조가 필요해지면 **문서를 고치지 않고 보고한다**. 어느 쪽이 맞는지는 사람이 판단한다.
- 품질 특성 간 트레이드오프(성능 vs 보안 등)를 에이전트가 임의로 선택하지 않는다.
- `FR` · `NFR` 에 근거가 없는 기능을 만들지 않는다. 업종에서 흔하다는 이유는 근거가 아니다.

**Rationale**: 요구 → PRD → SRS → 아키텍처 → 스펙으로 이어지는 추적 사슬은 이름으로 이어진다. 구현이 사슬 밖에서 이름을 만들면 추적이 그 지점에서 끊기고, 끊긴 것을 검증할 방법이 없다.

### II. 경계에서 판정한다 (기본 거부)

모든 요청은 업무 로직에 닿기 전에 **요청 경계 한 곳**에서 판정된다.

- 판정 순서는 고정이다. 기본 순서는 인증 → (여러 조직이 함께 쓰는 서비스면) 조직 문맥 → 권한 → 입력 스키마이며, 서비스에 맞게 고친 순서의 정본은 <판정 순서를 적은 문서 한 곳> 이다.
- 하나라도 실패하면 업무 컴포넌트를 호출하지 않는다. 판정할 수 없는 상태는 **거부**한다(Fail Secure).
- 데이터 소유 경계(사용자 · 조직)는 요청 경계와 데이터 접근 경계에서 **이중으로** 강제한다. 식별자를 직접 지정한 요청도 같은 판정을 거치고, 남의 기록은 「없음」과 같은 응답을 받는다.
- 화면에서 메뉴를 숨기는 것은 사용자 경험이며 방어선이 아니다. 방어선은 요청 경계뿐이다.
- 외부 입력은 경계에서 스키마로 검증하고, 경계를 통과한 뒤에는 신뢰한다. 검증 로직을 내부에 흩어 놓지 않는다.

**Rationale**: 판정이 여러 곳에 흩어지면 「모든 경로를 다 막았다」를 증명할 수 없다. 경계 차단 실패는 조용히 일어나므로 <경계 차단 실패 0건을 판정하는 NFR ID> 를 릴리스 실패 판정 지표로 둔다.

### III. 근거가 되는 기록은 고쳐 쓰지 않는다 (불변 이력) — 선택 원칙

**켜는 조건**: 돈 · 법적 근거가 되는 기록(결제 · 청구 · 약관 동의 · 감사 등)을 다루면 켠다. 대상 목록: <대상 기록 목록>. 대상이 없으면 이 원칙은 「해당 없음」으로 두고 게이트 4항을 건너뛴다.

- 대상 기록의 **취소는 상태 전환이며 물리 삭제가 아니다**. 수정은 변경 전후 값 · 행위자 · 시각을 추가 전용 이력으로 남긴다.
- 감사 기록에 수정 · 삭제 인터페이스를 만들지 않는다.
- 동시 수정은 **기록 버전 검사**로 막는다. 이력은 사후 추적이지 덮어쓰기 방어가 아니다.
- 파생값(금액 · 합계)은 저장된 결론이 아니라 근거 위에서 재현되는 값이다. 근거가 같으면 결과가 같아야 한다.
- **날짜 이력이 필요한 값과 아닌 값을 구분한다.** 지난 기록의 의미가 그날의 값에 묶이는 것(단가 · 요율 · 약관 버전)만 적용 시작일 이력으로 두고, 추정치 · 표시용 기준값은 고치면 지난 기록에도 새 값이 적용되는 단일 값으로 둔다. 어느 쪽인지는 값마다 결정(D-n)으로 남긴다. 이력 값을 처음 정할 때는 아주 이른 날짜부터 적용해 지난 기록이 값을 잃지 않게 한다.

**Rationale**: 근거 기록이 덮어써지면 「그때 왜 이 금액이었나」를 답할 수 없다. 반대로 모든 값을 이력으로 묶으면 사람이 「고쳤는데 지난 기록은 왜 그대로냐」를 겪는다. 값마다 어느 쪽인지를 결정으로 남기면 헌법과 결정이 어긋난 채 남지 않는다.

### IV. 재시도되는 모든 흐름은 멱등이다

재시도 · 재전송 · 배치 재실행이 있는 모든 경로는 같은 입력을 두 번 실행해도 결과가 같아야 한다.

- 멱등 키를 코드가 아니라 **설계에 명시**하고, 중복 도달 때의 동작(기존 기록 반환 · 건너뜀 · 합류)을 정의한다.
- 기기에 쌓았다가 다시 보내는 흐름은 「없으면 만들고 있으면 기존 기록을 돌려준다」이며 **서버에서 정정된 값을 덮어쓰지 않는다**.
- 배치는 두 번 돌려도 대상 건수와 합계가 변하지 않아야 한다.
- 사용자가 의도한 재실행(다시 보내기 버튼)과 네트워크 재시도를 키로 구분한다 — 키는 버튼 한 번 누름마다 새로 만든다.

**Rationale**: 건수와 금액이 재시도로 부풀면 그 사실을 사후에 발견할 방법이 없다. 12-Factor IX의 요구다.

### V. 12-Factor 실행과 벤더 비종속

- 환경에 따라 달라지는 값은 **전부 환경변수**다. 코드 · 설정 파일에 환경별 값을 두지 않는다.
- 프로세스는 **무상태**다. 세션 · 작업 상태를 프로세스 메모리나 로컬 디스크에 두지 않는다. 예외(기기 보관함 등)는 아키텍처 문서에 예외로 적힌 것만이다.
- 로그는 표준 출력 이벤트 스트림으로 내보내고 **전송처를 코드가 결정하지 않는다**.
- 백엔드 서비스(DB · 오브젝트 저장소 · 메일 · 문자 · 결제 · 외부 API)는 연결 자원이다. **벤더 SDK를 업무 코드가 직접 부르지 않는다** — 포트(인터페이스) 뒤에 두고 구현을 환경으로 고른다. 키가 없으면 그 기능은 꺼진 채 뜨고, 화면은 꺼져 있다는 사실을 보인다.
- 스키마 적용 · 정기 작업은 일회성 프로세스로 분리한다. 앱 코드에 관리 로직을 섞지 않는다.
- **서비스 기준 시간대는 코드 상수**다(실행 단위마다 한 곳). 환경변수로 두지 않는다 — 환경마다 같은 기록이 다른 날짜가 되면 안 된다.

**Rationale**: 같은 빌드 산출물이 로컬과 운영에서 그대로 돌아야 한다. 벤더 종속이 업무 코드에 스미면 배포처 · 사업자를 바꿀 때마다 다시 쓰게 된다.

### VI. 실패 케이스 우선 테스트 (NON-NEGOTIABLE)

- 테스트는 **구현과 같은 커밋**에 넣는다. 뒤로 미루지 않는다.
- 스펙에 정의된 실패 시나리오(타임아웃 · 인증 실패 · 권한 거부 · 부분 실패 · 중복/재시도 · 경계 위반)는 **반드시 테스트로 존재**한다. happy path만 있는 테스트는 미완성이다.
- 테스트 이름은 `{대상}_{시나리오}_{기대결과}` 로 시나리오를 서술하고, 본문은 Given-When-Then으로 나누며 한 테스트에 When은 하나다.
- 저장 계층은 실제 테스트 인스턴스로 검증한다. mock/stub은 외부 API에만 쓴다.
- `FR` 의 Acceptance Criteria는 **그대로 테스트 케이스가 된다**. AC와 테스트의 대응이 끊기면 그 `FR` 은 미완성이다.
- 커버리지 숫자가 아니라 시나리오 커버리지로 판정한다.

**Rationale**: 기록 서비스의 실패는 조용하다 — 틀린 합계, 새는 경계, 사라진 미전송 건은 오류 화면을 띄우지 않는다. 실패 경로에 테스트가 없으면 실패를 관측할 수단이 없다.

### VII. 의존은 안쪽으로만 흐른다 (클린 아키텍처 · SOLID)

- 의존 방향은 바깥(세부사항) → 안(정책) 한 방향이다. 도메인 로직은 프레임워크 · DB · UI · 외부 API를 모른다.
- 컴포넌트 간 접근은 **공개 인터페이스로만** 한다. 상대의 내부 모듈 · 테이블을 직접 읽지 않는다.
- 순환 의존을 만들지 않는다. 컴포넌트 호출 방향(<컴포넌트 문서의 호출 방향 절>)을 어기는 호출은 거부 사유이며, 아키텍처 테스트로 고정한다.
- SRP: 한 모듈이 두 가지 이유로 바뀌면 나눈다. DIP: 도메인이 구현체를 직접 만들지 않고 경계에서 주입받는다.
- 추상화는 문제가 있을 때만 들인다. 구현체가 하나뿐인 인터페이스(포트 제외), 제품이 하나뿐인 팩토리, 변하지 않는 값의 설정은 만들지 않는다.

**Rationale**: 컴포넌트 경계는 사람이 승인한 구조다. 코드가 그 경계를 가로지르면 다이어그램이 거짓말이 되고, 다음 사람은 문서를 믿지 못해 전부 다시 읽는다.

## 추가 제약 — 기술 스택 · 보안 · 민감 데이터

**기술 스택은 결정 사항이며 요구가 아니다.** 스택이 바뀌는 결정은 이 표를 고치는 MINOR 개정과 같은 작업에 묶는다(표가 실제와 어긋난 채 남지 않게). **이 템플릿은 스택을 정하지 않는다** — 스택을 고르면 ADR(`docs/04.design/01.architecture/02.adr/`)을 쓰고 이 표를 채운다. 표가 비어 있는 동안 계획(`plan.md`)의 Technical Context 는 「미정 — ADR 필요」로 적고 구현을 시작하지 않는다.

| 대상 | 결정 | 근거 ADR |
| --- | --- | --- |
| 서버 · 정기 작업 | <언어 · 프레임워크 · 빌드 도구> | <ADR-NNN> |
| 저장소 | <종류 · 스키마 정본 위치 · 이행 방식> | <ADR-NNN> |
| 클라이언트 | <종류 · 프레임워크 — 없으면 「없음」> | <ADR-NNN> |
| 실행 · 배포 | <로컬 실행 · 운영 배포 방식> | <ADR-NNN> |

**보안 (위반 시 병합 금지)**

- 시크릿 · API 키 · 비밀번호 · 토큰을 소스코드에 **절대 하드코딩하지 않는다**. 전부 환경변수로 받는다.
- 질의는 파라미터 바인딩만 쓴다. 문자열 조합 금지.
- 비밀번호는 검증된 느린 단방향 해시(`argon2id` 등). 자체 구현 암호화 금지.
- CORS 허용 오리진은 환경변수로 받은 명시 목록. `*` 금지.
- 인증 · 인가는 모든 진입점에서 처리 전에 검증한다. 「내부에서만 호출된다」는 가정 금지.

**민감 데이터**

- 보호 대상 필드 목록의 정본은 <민감 필드를 정한 NFR ID> 한 곳이다. 다른 문서는 목록을 옮겨 적지 않고 그 ID를 가리킨다.
- 시크릿 · 토큰 · 금액 · 연락처를 로그 본문과 오류 메시지에 남기지 않는다.
- 사용자에게 보이는 오류에 스택 · 쿼리 · 내부 경로를 노출하지 않는다.
- 테스트 픽스처에 실제 고객 데이터를 넣지 않는다. 생성기나 가짜 값(`conventions.md` 의 예시 값)을 쓴다.

## 개발 워크플로와 품질 게이트

**작업 순서**: `speckit-specify` → `speckit-clarify`(선택) → `speckit-plan` → `speckit-tasks` → `speckit-analyze`(선택) → `speckit-implement`. 각 단계는 사람 검토로 게이트된다. 스펙 형식(정식 · 델타 · 경량 · 문서 단위 · 보류)의 선택 기준은 `specs/README.md`, 단계 · 게이트 · 역할은 `.claude/rules/workflow` 가 정본이다.

**브랜치와 커밋**

- 브랜치 · 커밋 형식과 운영 모드(팀 · 1인 로컬)는 `.claude/rules/git-workflow.md` 를 따른다.
- 커밋은 수동이다. Spec Kit 자동 커밋 훅에 맡기지 않는다.
- 하네스 파일(`CLAUDE.md` · `.claude/**`)은 작업 중에 임의로 고치지 않는다 — 고칠 곳은 스펙의 「문서 갱신 제안」으로 남기고, 소유자가 지시한 작업에서만 고친다. 예외는 `speckit-plan` 이 바꾸는 `CLAUDE.md` 의 `SPECKIT START/END` 블록과 결정 색인 새 행이다(`.claude/rules/decisions` §7).

**병합 전 게이트 (전건 통과해야 한다)**

1. 대상 `FR` 의 Acceptance Criteria 전건에 대응하는 테스트가 있고 통과한다.
2. 실패 케이스 테스트가 최소 1건 있다(원칙 VI).
3. 요청 경계 판정을 우회하는 경로가 새로 생기지 않았다(원칙 II).
4. 이력 · 감사 기록이 필요한 변경에 기록 코드가 함께 있다(원칙 III — 켠 경우).
5. 재시도 경로가 있으면 멱등 테스트가 있다(원칙 IV).
6. 환경별 값 하드코딩 0건, 벤더 SDK 직접 호출 0건(원칙 V).
7. 컴포넌트 경계를 넘는 직접 접근 0건, 순환 의존 0건(원칙 VII).
8. 민감 데이터가 로그 · 오류 · 픽스처에 없다.

**잠정 결정의 취급**: 요구 문서의 수치(응답 시간 · 한도 · 보관 기간)는 **합격선이지 결론이 아니다**. 측정으로 바뀔 값은 코드에 흩어 놓지 않고 설정 한 곳에 모은다. 모르는 값은 지어내지 않고 「미정」과 선정 기준을 적는다.

## Governance

- 이 문서는 다른 관행보다 우선한다. `.claude/rules/` 와 충돌하면 이 문서가 이기고, 충돌 사실을 PR(또는 작업 보고)에 적는다.
- **결정과 헌법의 충돌**: 결정(D-n)이 이 문서의 원칙을 건드리면 그 결정 행에 「헌법 개정 필요」를 적고 아래 개정 절차를 탄다. 개정 전까지 결정을 적용하지 않거나, 적용했다면 Sync Impact Report 의 ⚠ 줄로 남긴다. 결정 표와 원칙의 대조는 사람이 G1 에서 한다(`.claude/rules/workflow` §2) — `speckit-analyze` 는 요구 · plan 요소를 원칙과 맞춰 보지만 결정 표 행을 하나씩 훑지 않는다.
- **개정 절차**: 변경 제안 → 영향 받는 템플릿 · 문서 목록 작성 → 사람 승인 → 이 문서와 의존 문서를 같은 작업에서 갱신 → Sync Impact Report 를 새로 쓴다.
- **버전 정책** (semantic versioning):
  - MAJOR — 원칙 삭제 · 재정의 등 하위 호환이 깨지는 거버넌스 변경
  - MINOR — 원칙 · 절 신설 또는 실질적 확장(기술 스택 표 변경 포함)
  - PATCH — 표현 정리, 오타, 의미가 바뀌지 않는 보완
- **준수 검토**: 모든 병합은 「병합 전 게이트」 8항목을 확인한다. 복잡도를 늘리는 변경은 이유와 버린 더 단순한 대안을 적는다.
- **런타임 지침**: 일상 작업 지침은 `CLAUDE.md` 와 `.claude/rules/` 를 따른다. 이 문서는 그 위에 있는 게이트다.
