# 아키텍처 결정 기록 (ADR)

이 디렉터리는 아키텍처 결정 기록을 담는다. 파일명은 `NNN-<짧은-설명>.md`이며 번호는 `001`부터 결번 없이 순차로 붙인다. 새 기록은 [000-template.md](000-template.md)를 복사해서 시작한다.

**ADR은 사람이 쓴다**([code-principles.md](../../../../.claude/rules/code-principles.md) §1). 에이전트는 커버리지 검사와 갭 감사에서 **결정이 필요하다고 드러난 후보**를 아래 §3에 올리기만 하고, 결정 자체를 여기 쓰지 않는다. 결정이 나면 사람이 ADR을 쓰고, 영향받는 설계 문서에 개정 블록을 단다.

---

## 1. 해소된 갭 (스펙에 반영 완료)

커버리지 검사(`G-n`)에서 나와 사람의 결정으로 닫힌 갭이다.

| # | 갭 | 결정 | 반영 위치 |
| ---: | --- | --- | --- |
| `G-n` | <갭 한 줄> | <결정 요약 · D-n> | <FR · 설계 문서 §> |

---

## 2. 갭 감사 결과

렌즈 n개 × 적대적 반박 2인으로 SRS · 설계 문서를 대조한 결과다([diagram-workflow](../../../../.claude/rules/architecture-diagram/diagram-workflow) §1.1). 후보 수 · 생존 수 · 탈락 사유를 적고, 생존한 것만 스펙에 반영한다.

| # | 갭 | 반영 |
| ---: | --- | --- |
| 1 | <갭> | <신설 · 개정한 FR · NFR> |

> **가장 위험했던 것은 n번이다.** <틀려도 오류가 뜨지 않고, 복구할 수 없는 이유 한두 문장>

### 2.1 감사가 다루지 못한 영역

<렌즈가 편중돼 같은 강도로 보지 못한 영역 — 예: 도메인 계산 정확성. 별도 감사가 필요한 범위>

---

## 3. 결정이 필요한 ADR 후보

| # | 결정 필요 사항 | 근거 | 출처 |
| ---: | --- | --- | --- |
| 1 | **기술 스택** — 언어 · 프레임워크 · 저장소 · 실행 환경 | 이 템플릿은 스택을 정하지 않는다. NFR(성능 · 가용성 · 운영 인력)과 팀의 숙련을 근거로 고른다 | [02_c4_container](../01.diagram/02_c4_container.md) A-1 |
| 2 | 업무 데이터베이스 직접 접근 경로의 통제 방식 | 통제가 없으면 권한 판정이 애플리케이션 밖에서 우회된다 | [07_deployment_architecture](../01.diagram/07_deployment_architecture.md) A-2 |

위 두 행은 예시 도메인(공유 회의실 예약)의 견본이다. 1번은 어느 프로젝트에서나 첫 ADR이 된다.

## 4. 다이어그램 도구 결정

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 다이어그램 원본 | **Mermaid** (문서 안 블록) — 1차 도구 | git 이력에 글자로 남아 변경을 diff로 추적한다. GitHub · 편집기가 설치 없이 그린다 |
| 열람용 렌더 | 선택 — archify 같은 렌더 플러그인을 추가로 쓸 수 있다 | 발표 · 검토용으로 한 장에 조망하기 쉽다. **내용은 Mermaid와 같아야 한다** |
| 같은 그림의 두 번째 원본(다른 문법 · 그림 파일만) | 두지 않음 | 두 벌이 되면 한쪽이 낡는다 |

프로젝트가 다른 도구를 고르면 이 표와 [diagram-workflow](../../../../.claude/rules/architecture-diagram/diagram-workflow) §6을 같이 고친다.
